# S3 제3판 마감 지시서

두 검증 에이전트(수정 실효성 검증 · 요구사항 재감사)의 결과를 호출자가 판정한 것이다.

**먼저 알아 둘 것 — 제2판은 성공했다.**
- 요구사항 **42/42 SATISFIED** (PARTIAL 0 · UNSATISFIED 0 · CLAIMED-ONLY 0)
- 브리핑 35항목 중 **33 CLOSED / 2 PAPER / REGRESSED 0**
- **§D 승인 목록 6건 전부 무손상** — 부수 피해 없음
- 결정 ID `D-SH1`~`D-SH17`, `D-PS1`~`D-PS10` **각각 정확히 한 번 정의**, 중복·미정의 인용 0

**이것은 재작성이 아니라 마감이다.** 구조를 바꾸지 마라. 아래 항목만 수술적으로 고쳐라. 특히 §6의 목록과 이미 CLOSED로 판정된 결정을 건드리지 마라.

## §1. 개정이 만든 새 모순 — 최우선

### P1. `D-PS4` 재진입 가드가 `D-PS10`과 §10.1을 무효화한다 (최고 가치 발견)

§8.4는 `Republish` 실행 구간에서 `IConditionSink.Set` / `IErrorSink.Report` / `Settings.Update` 호출을 재진입 위반으로 잡고, N3 수정으로 **Release에서도** 보고한다. 그런데:

- §10.1의 구독자별 catch가 **그 구간 안에서** `IErrorSink.Report`를 부른다.
- `D-PS10`(B3의 수정)이 **그 구간 안에서** 조건을 세운다.

**결과** — 격리된 `Refresh` 실패마다 허위 재진입 보고가 Release에서 발생하고, **B3의 표면화 기제 전체가 자기가 공유하는 패스의 가드를 밟는다.** N3와 B3를 각각 옳게 반영했으나 맞물림을 확인하지 않았다.

**조치** — 가드의 대상을 정확히 다시 정의하라. 재진입 가드가 막으려던 것은 *"`Refresh`가 상태를 변경해 또 다른 게시를 유발하는 것"*이지 *"실패를 보고하는 것"*이 아니다. 최소한 다음을 구별하라:
- **금지**: `Settings.Update`, 그리고 새 스냅샷 게시를 유발할 수 있는 모든 호출.
- **허용(가드 면제)**: §10.1의 catch가 내는 `IErrorSink.Report`와 `D-PS10`의 조건 설정. 이 둘은 진단 경로이며 `Republish`를 재유발하지 않는다 — **다만 그것이 참인지 명시적으로 논증하라.** `IConditionSink.Set`이 `Store` 스냅샷을 바꾸고 그것이 `SnapshotChanged`를 낳는다면 참이 아니다. 참이 아니라면 조건 설정을 패스 **바깥**으로 미루는 쪽을 택하라(예: 패스 종료 후 1회 반영).

이 논증이 이 항목의 핵심이다. 결론보다 논증을 정확히 써라.

### P2. B7이 한 문단 안에서 반대 결론 두 개를 낸다

§6.5: *"구버전 파일…에서는 안내를 다시 띄우지 않는 것이 낫다. 판정은 플래그의 부재 자체로 한다 — 필드가 없거나 `false`면 안내를 띄운다."* 앞 문장의 선호와 뒤 문장의 결정이 정반대다.

**조치** — 하나로 정하라. 권고: **뒤 문장(부재 = 안내 표시)을 채택**하고 앞 문장을 삭제하라. 근거 — 구버전 파일에서 올라온 사용자도 트레이 아이콘이 오버플로에 숨는다는 사실(측정 §4.1)을 겪는 것은 같으므로 안내가 유효하다. 다른 결론을 택해도 좋으나 **한쪽을 지워라.**

## §2. 차단 수정의 빈 링크

### P3. B1의 전송 링크가 없다 — 도달성 폴백이 조용히 작동하지 않는다 (High)

§3.2가 수신부(`HWND_MESSAGE` 메시지 전용 창 + `RegisterWindowMessage`)를 정의했으나 **두 번째 인스턴스가 그 창을 어떻게 찾는지**를 정의하지 않았다.

**핵심 사실**: `HWND_BROADCAST`는 **메시지 전용 창에 전달되지 않는다.** 따라서 `D-SH4`(메시지 전용 창)와 브로드캐스트를 결합하면 `D-SH14`(신호 → 설정 창 표시, B1의 폴백)가 **무력화된다.** 트레이가 죽었을 때 마지막 회수 수단이 조용히 사라진다는 뜻이다.

**조치** — 발견 기제를 정하라. 표준 해법은 등록된 클래스 이름으로 `FindWindowEx(HWND_MESSAGE, null, className, null)`을 호출하는 것이다. 클래스 이름 문자열 자체는 → S4로 유예해도 좋으나 **기제와 그것이 `HWND_MESSAGE` 아래를 탐색해야 한다는 사실은 지금 확정하라.**

추가로, HLD D18-d의 **무응답 분기**는 응답(ack)을 전제하는데 §3.2의 핸들러는 응답을 보내라는 지시를 받은 적이 없다. 응답 여부와 그 형태를 정하거나, 무응답 분기를 개정 요구로 올려라.

### P4. `ViewModelRefreshFailing`에 갈 곳이 없다 — **두 검증이 독립적으로 짚었다**

`D-PS10`이 `IConditionSink`로 **저장 조건**을 세우지만 `AppConditionKind`는 **S2 §2.11에 동결된 닫힌 열거형**이고, S2는 `Store`가 그 저장 그룹 밖의 `SetCondition`을 **거부한다**고 명시한다. 즉 설계대로 구현하면 런타임에 거부되어 B3의 수정이 스스로를 무효화한다.

대조가 뼈아프다 — §3.2의 M10은 정확히 이 문제를 피하려 `SettingsWriteFailed`를 **재사용**했는데 §10.1은 그러지 않았다.

**조치** — 둘 중 하나를 택하고 근거를 적어라:
- **(a) 기존 종류 재사용.** 가장 싸다. 다만 "뷰모델이 갱신에 실패한다"를 기존 어느 종류로도 정직하게 표현할 수 없다면 택하지 마라.
- **(b) 새 종류 신설.** 그렇다면 **세 곳 전부**를 개정 요구로 올려라 — ① S2 §2.11 `AppConditionKind` 열거형(저장 그룹) ② HLD §6.4 행(진입·해제·표시 위치) ③ S3 §5.4/§5.5 배너 목록. `LoggingUnavailable`이 §13-16에서 받은 것과 **정확히 같은 등록**이다.

### P5. M10·M5의 행위자가 없다 (Med)

- **M10** (§3.2, 종료 flush 흔적): 재사용할 조건(`SettingsWriteFailed`)은 정했으나 *"`IConditionSink.Set` 호출은 6번(`Store` 등록) 이후로 큐잉하거나 … 6번 등록 직후로 미룬다"*고 적었다. **DI 등록은 전부 어떤 `StartingAsync`보다도 먼저 끝나므로 "6번 등록 직후"는 런타임 시점이 아니다.**
- **M5** (`LoggingUnavailable`): 진입이 *"`Diagnostics` 파일 로거 오픈 실패(Main 1번)"* — DI가 존재하기 이전이다. `Store`가 살아난 뒤 누가 조건을 세우는지 없다.

**조치** — 둘 다 **누가 검출 결과를 보관하고, 어느 수명주기 지점에서 `Set`을 부르는가**를 정하라. 부팅 초기 검출 결과를 담는 자리(예: 컴포지션 루트가 들고 있다가 `StartAsync` 이후 1회 반영)를 하나 정의하면 둘이 같은 기제를 쓴다.

### P6. B5 — 워치독 타이머가 §3.3-a에 없다 (Low)

§13-8은 *"§3.3 a단계에 `IUiTicker.Stop()`과 함께 정지 시점을 명시"*했다고 주장하나, §3.3-a는 네 항목(구독 해제 · `IUiTicker.Stop` · 팬아웃 구독 해제 · 신호 비활성화)만 열거하고 **워치독이 없다** — B5가 지목한 다섯 객체 중 하나다.

### P7. E3가 존재하지 않는 후크에 조건부로 걸려 있다 (PAPER)

§4.0.2: *"S2 §11에 렌더링 품질 검증 항목을 **두게 되면** … 화면 캡처만 유효하다고 명시한다 … 지금은 경고로만 남긴다."* 조건절의 후크가 존재하지 않고, S2 §11에 대한 §13 개정 요구도 §14 유예 목록도 없다.

**조치** — S2 §11에 **"렌더링 품질 검증은 화면 캡처로만 한다. `RenderTargetBitmap`은 화면 안티에일리어싱을 반영하지 않으므로(측정 §8.4) RTB 기반 단언은 무효다"** 항목을 추가하라는 개정 요구를 §13에 올려라. 조건절을 없애라.

## §6. 건드리지 말 것 (재확인)

검증이 **무손상 생존**을 확인한 것들이다:

`D-SH3` 등록 순서와 그 근거 · `D-PS1`(N8-②로 `DispatcherPriority` 확장한 것은 옳은 해소다) · `D-PS2`/`D-PS3` 병합(정상 경로 재설계 금지) · `Store` 4얼굴 1회 등록 · `D-SH4` 메시지 전용 창(B1의 하중을 진다) · `Owner` 반전 · 이동 모드 해체 §4.6.2.

그리고 **요구사항 42/42는 이미 달성됐다.** 이 마감에서 요구사항 충족을 다시 논증하지 마라 — 무너뜨리지만 마라.
