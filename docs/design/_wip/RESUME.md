## 0. 지금 막고 있는 것

### ⚠ 이 장비에서 WPF 하드웨어 렌더링이 픽셀을 내지 않는다

**앱의 결함이 아니다.** 평범한 불투명 WPF 창을 별도 프로세스로 띄워도 화면 기여가 0이고, 프로브에서 `RenderOptions.ProcessRenderMode = SoftwareOnly` 하나만 바꾸면 즉시 정상 렌더된다. 실행 중인 오버레이는 화면에서 **검은 사각형**이다 — 색상이 딱 둘(컬러키로 비친 배경, 자식이 그린 검정)이고 α 합성 산술까지 맞는다.

**2026-08-16 14시경에는 정상이었다** — 아티팩트의 스크린샷이 그때 것이다. 그 사이 상태가 바뀌었다.

**다음 세션에서 할 일**: 재부팅 후 앱을 실행한다.
- **글자가 보이면** → 장비 문제였다. ClearType 재측정을 진행한다(§1).
- **여전히 검은 사각형이면** → 앱의 결함이다. 소프트웨어 렌더링 강제를 포함해 다시 봐야 한다.

캡처 경로 자체는 해결됐다 — `BitBlt`와 `Windows.Graphics.Capture` 모니터 캡처가 픽셀 단위로 일치함을 확인했다. 측정 리그도 만들어져 있다(`00-shell-measurements.md` §13.5.5에 조리법).

## 3. 작업 방식 (유지할 것)

- **단계마다 같은 루프**: 구현 → 리뷰 → 호출자가 타당성 판정 → 수정 → 커밋.
- **설계 문서가 코드보다 먼저** (`CLAUDE.md`).
- 대용량 문서는 컨텍스트로 통과시키지 않는다. 에이전트가 파일에 직접 쓰고 요약만 받는다.
- 리뷰는 모아서 한 번에. 브리핑에 **「건드리지 말 것」 목록**을 반드시 포함한다.
- **설계가 틀렸으면 우회하지 말고 보고하게** 한다 — 매 단계에서 가장 값진 산출이 여기서 나왔다.

## 4. 측정이 신뢰를 잃은 여섯 가지 방식

실측이 설계를 **열여덟 번** 뒤집었고, 그중 여섯은 **우리 자신의 측정**이 틀린 경우였다.

| 양식 | 사례 |
|---|---|
| 경쟁 가설을 구별하지 못하는 실험 | `PeriodicTimer.Period` — 초기 관측이 두 해석 모두와 양립했다 |
| 정답과 오답이 우연히 같은 값 | 행 5의 `r / v`와 API의 `maxVolumeRate`가 문자 단위로 일치 |
| 끝난 상태만 검사 | 트리거 병합 순서 — 두 규칙 모두 같은 결말이라 구별 불가. 후행 틱이 필요했다 |
| 측정 대상과 명세 대상이 다름 | 「7패스 수렴」은 명령 하나를 큐잉할 때의 값인데 설계는 둘을 큐잉했다 |
| **시험 대상 구성이 성립한 적 없음** | 「레이어드 WPF 창이 ClearType 유지」 — 스타일 비트가 조용히 걸러진 불투명 창을 쟀다 |
| **예상한 것만 확인하고 전체를 열거하지 않음** | 이름 출처 — `core.items` 안의 `divine`을 보고 기록했으나 그 배열에 둘뿐임을 세지 않았고 문서 루트를 열거하지 않았다 |

**「측정했다」가 「구별했다」를 보장하지 않는다.**

## 5. 테스트가 거짓말한 세 가지 방식

| 양식 | 사례 |
|---|---|
| 버그 형태 자체를 단언 | 유계 큐 테스트가 `DroppedCount == 3`을 단언했는데 그게 무한 증가의 모양이었다 |
| 개수만 세고 무엇인지 안 봄 | 트리거 병합 테스트가 라운드 수만 셌다 |
| 가짜 클록이 차이를 지움 | `FakeTimeProvider`가 흐르지 않아 구독자마다 시계를 따로 읽어도 값이 같았다 |

**새 회귀 테스트는 가드를 되돌려 실패를 본 뒤에야 믿는다.**

## 6. 환경 메모

- **WPF 하드웨어 렌더링이 캡처에 안 잡히는 것과 아무것도 그리지 않는 것은 다른 문제다.** 후자가 현재 상태다(§0).
- `HKCU\SOFTWARE\Microsoft\Avalon.Graphics`가 **값 없이 빈 키로** 존재한다. WPF 런타임이 만드는 것이며 `DisableHWAcceleration`은 없다. 동작에 영향 없음.
- `%APPDATA%\PoeOverlay\settings.json`에 캡처 작업이 넣은 관심목록 항목이 남아 있을 수 있다.
