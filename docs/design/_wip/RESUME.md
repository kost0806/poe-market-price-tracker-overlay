## 0. 남은 일

### 6단계 — `Shell` **(진행 중)**

WPF 창 · Win32 상호운용 · 트레이 아이콘 · 컴포지션 루트, 그리고 낡은 `src/PoeOverlay/` 제거.

**이 단계는 측정 문서가 곧 명세다.** 단위 테스트가 닿지 않으므로 `00-shell-measurements.md` §1~§10과의 일치가 correctness의 정의다. 특히 **하지 말아야 할 것들**:

- 확장 스타일·`Topmost` **재적용 코드 금지** (리사이즈·모니터 이동을 견딘다는 측정이 이걸 막으려고 기록됐다)
- `NotifyIcon` **재등록 코드 금지** (`TaskbarCreated`에 자가 복구)
- **`AttachThreadInput` 금지** — 우회가 아니라 포그라운드 잠금 뚫기다
- `window.IsActive`로 활성화 판정 **금지** (실패한 모든 사례에서 `True`였다)
- `Shell_NotifyIconGetRect`의 HRESULT **불신** (`S_OK`와 함께 틀린 rect를 반환했다)

검수는 빌드·테스트만이 아니라 **앱을 실제로 기동·종료**시켜 확인한다.

### 6단계 이후

리뷰 → 타당성 판정 → 수정 → 커밋. 그다음 남는 것은 실사용 검증뿐이다:

- **DirectX 독점 전체화면 미측정** — 대역 WPF 창으로는 재현 불가. 실물 PoE로 1회 확인 필요
- **색 팔레트·폰트 크기 잠정값** — S3 §14-12의 판독성 실험 후 교체
- **60 Hz 화면 미측정** (측정은 165 Hz에서 수행)

## 2. 작업 방식 (유지할 것)

- **단계마다 같은 루프**: 구현 에이전트 → 리뷰 에이전트 → 호출자가 타당성 판정 → 수정 발주 → 커밋.
- **대용량 문서는 컨텍스트로 통과시키지 않는다.** 에이전트가 파일에 직접 쓰고 요약만 받는다.
- **리뷰는 모아서 한 번에** 넘긴다. 쪼개면 충돌하는 수정이 들어온다.
- **브리핑에 「건드리지 말 것」 목록을 반드시 포함**한다. 빠뜨리면 이미 옳은 결정이 부수 피해를 입는다.
- **설계가 틀렸으면 우회하지 말고 보고하게** 한다. 이 지시가 매 단계에서 가장 값진 산출을 냈다.

## 3. 측정이 신뢰를 잃은 네 가지 방식

이 프로젝트에서 실측이 설계를 **열일곱 번** 뒤집었고, 그중 넷은 **우리 자신의 측정이 틀린** 경우였다. 기록해 둘 값어치가 있다.

| 양식 | 사례 |
|---|---|
| **경쟁 가설을 구별하지 못하는 실험** | `PeriodicTimer.Period` — 초기 관측이 두 해석 모두와 양립했다. 재측정하니 대기가 변경 시점부터 **다시 시작**한다(5분→30분을 3분째에 = 33분 뒤) |
| **정답과 오답이 우연히 같은 값** | 행 5의 `r / v`와 API의 `maxVolumeRate`가 문자 단위로 일치해, 지름길을 써도 테스트가 통과한다 |
| **끝난 상태만 검사** | 트리거 병합 순서 — `[Scheduled, Scheduled, Repoll]`은 두 규칙 모두 Repoll로 끝나 구별되지 않았다. 후행 틱이 필요했다 |
| **측정 대상과 명세 대상이 다름** | 「7패스 수렴」은 명령을 하나 큐잉할 때의 값인데 설계는 둘을 큐잉하라고 적었다(→ 9패스) |

**「측정했다」가 「구별했다」를 보장하지 않는다.**

## 4. 테스트가 거짓말한 세 가지 방식

| 양식 | 사례 |
|---|---|
| **버그 형태 자체를 단언** | 유계 큐 테스트가 `DroppedCount == 3`을 단언했는데 그게 무한 증가의 모양이었다 |
| **개수만 세고 무엇인지 안 봄** | 트리거 병합 테스트가 라운드 수만 셌다 |
| **가짜 클록이 차이를 지움** | `FakeTimeProvider`가 흐르지 않아, 구독자마다 시계를 따로 읽어도 값이 같았다 |

**새 회귀 테스트는 가드를 되돌려 실패를 본 뒤에야 믿는다.** 매 단계에서 이 증거를 요구했다.
