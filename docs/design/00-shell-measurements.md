| | |
|---|---|
| 문서 상태 | **실측 확정 · 구속력 있음** |
| 측정일 | 2026-08-15 |
| 측정 환경 | Windows 11 Pro 10.0.26200 · .NET SDK 8.0.424 · 주 모니터 2560×1440 |

> **PoE 실물로 측정하지 않았다.** 게임 대역으로 WPF 창(`WindowStyle=None`, `WindowState=Maximized`, `Topmost=true`)을 썼다. DirectX **독점 전체화면**은 이 방법으로 재현할 수 없으며 **더 나쁠 것이 거의 확실하다**(§5).

## 0. 결론 두 줄

1. **활성화는 된다.** 트레이 클릭 핸들러에서 `Show(); Activate();` 만으로 포그라운드를 가져온다. 테두리 없는 전체화면 `Topmost` 창이 직전까지 포그라운드를 쥐고 있어도 성공한다. **어떤 우회 기법도 필요하지 않다.**
2. **그러나 트레이 아이콘에 손이 닿지 않는다.** 게임이 화면을 덮고 있는 동안 작업표시줄이 게임 아래로 내려가 아이콘을 **클릭할 수 없다.** 좌표를 정확히 찍어 넣은 클릭이 트레이가 아니라 게임 창에 떨어졌다.

**따라서 Q17의 답은 "예, 단 트레이에 도달할 수 있다면"이고, 게임 중에는 도달할 수 없다.**

## 1. Q17-A — 포그라운드 활성화

### 1.1 성공 사례

| 상황 | 결과 | 비고 |
|---|---|---|
| 게임 없음 | **성공** | FG: explorer 오버플로 플라이아웃 → `Q17_SETTINGS` |
| 평범한 최대화 창이 FG | **성공** | |
| **테두리 없는 전체화면 + `Topmost`** 가 FG | **성공** | 작업표시줄을 띄우기 위해 Win 키 선행 |
| 테두리 없는 전체화면 (non-topmost) | **성공** | 동일 |

여섯 가지 활성화 변형(순정 / `SetForegroundWindow` / `AllowSetForegroundWindow`+SFW / `AttachThreadInput` / `SetWindowPos(HWND_TOPMOST)`+복원 / `Topmost` 토글)이 **전부 동일하게 성공**했다. 필요한 것도, 해를 끼친 것도 없다.

### 1.2 음성 대조군 — 성공이 우연이 아님을 보이는 근거

| 상황 | 결과 |
|---|---|
| `DispatcherTimer`에서 활성화, **사용자 입력 0**, 전체화면 창이 FG | **실패** (`everBecameForeground=False`) |

대조군이 실패하므로 §1.1의 성공은 "마침 아무도 포그라운드를 쥐지 않았다"는 인공물이 아니다. **트레이 클릭이 프로세스에 포그라운드 권리를 부여한다**는 것이 실제로 측정됐다.

### 1.3 필요한 코드 — 없다

```csharp
_tray.MouseUp += (s, e) =>            // 이미 WPF UI 스레드에서 돈다
{
    _settings ??= new SettingsWindow { Owner = _overlayWindow };  // Owner ⇒ WS_EX_TOPMOST 상속
    _settings.Show();
    _settings.Activate();
};
```

`Owner` 지정은 활성화를 위한 것이 **아니라** z-순서를 위한 것이다(§2).

### 1.4 쓰지 말아야 할 것

| 기법 | 측정 결과 | 처분 |
|---|---|---|
| `AttachThreadInput` + `SetForegroundWindow` | **잠금을 완전히 무력화한다** — 사용자 입력 0에서도 성공했다 | **금지.** 우회가 아니라 **잠금 우회(bypass)**다. 채택하면 오버레이가 게임에서 포커스를 뺏을 수 있는 수단을 갖게 된다 |
| `AllowSetForegroundWindow(ASFW_ANY)` 자기 자신에게 | **무의미.** 잠긴 경우 `False` 반환, FG 변화 없음 | 다른 프로세스에게 **주는** API다. 자기적용은 아무 일도 하지 않는다 |
| `window.IsActive`로 성공 판정 | **거짓말한다.** **실패한 모든 사례에서 `True`였다.** `GetActiveWindow`/`GetFocus`도 스레드 지역이라 같다 | 판정은 **`GetForegroundWindow()` 하나로만** 한다 |

### 1.5 도달성 — Q17이 실제로 막힌 지점

| 상황 | 결과 |
|---|---|
| 전체화면(`Topmost`)이 화면을 덮은 상태에서 트레이 아이콘 좌표 (2310,1416) 클릭 | **`PROBE_TARGET_fullscreen`에 떨어졌다.** `TrayNotifyWnd`가 아니다 |
| 전체화면(non-topmost)에서 동일 | **동일하게 실패** |
| Win 키를 먼저 눌러 작업표시줄을 띄운 뒤 클릭 | **성공** |

Windows의 전체화면 감지가 작업표시줄을 게임 아래로 강등한다. `Topmost` 여부와 무관하다.

**함의**: `REQUIREMENTS.md` §2가 전역 핫키를 제외하며 적은 근거 — *「트레이 아이콘이 진입점을 제공하므로 불필요」* — 는 **측정으로 반증됐다.** 게임 중에 트레이는 진입점이 아니다.

## 2. Q17-B — `Owner`가 TOPMOST를 전파한다

| 측정 | 결과 |
|---|---|
| `Owner = overlay(Topmost=true)`인 창의 `GWL_EXSTYLE` | `0x40108` — **`WS_EX_TOPMOST` 설정됨.** 단 `owned.Topmost == false` |
| Owner 없는 창 | `0x40100` — TOPMOST 없음 |
| `overlay.Topmost = false`로 되돌리면 | 소유 창도 `0x40100`으로 **함께 내려간다** (제거도 전파된다) |
| Owner 없는 설정 창의 z-순서 | `owned > overlay > unowned` — **오버레이 뒤로 숨는다** |
| 트레이에서 연 소유 창 | 활성화 성공 **그리고** 오버레이 위에 렌더 |

**결정 입력**: 설정 창은 **`Owner = 오버레이`로 만든다.** 소유하지 않으면 항상 위에 뜨는 오버레이 뒤로 사라진다. `Topmost` 속성은 `false`로 두어도 상속된 exstyle이 일한다.

## 3. Q17-C — NOACTIVATE 오버레이는 포그라운드를 빼앗지 않는다

`Show()`, 내용 변경·이동·`Topmost` 재설정·`Hide`/`Show` 5회, 그리고 **명시적 `Activate()` 호출**까지 — 전체화면 창이 FG를 유지했다. exstyle은 `0x80801A8`로 고정.

**`WS_EX_NOACTIVATE`는 명시적 `Activate()`조차 무해하게 만든다.** 오버레이가 실수로 게임에서 포커스를 뺏을 경로가 구조적으로 없다.

## 4. Q17-D — 트레이 아이콘

| # | 측정 | 결과 |
|---|---|---|
| D1 | 순수 WPF `Application`(WinForms 메시지 루프 없음)에서 `NotifyIcon` | **동작한다.** `UseWindowsForms=true`만 있으면 된다. 등록·클릭 전달 정상 |
| D2 | 클릭 핸들러가 도는 스레드 | **WPF UI 스레드.** `Dispatcher.CheckAccess()==True`, WPF `Window`를 직접 만져도 된다. **`Dispatcher.Invoke` 불필요** |
| D3 | `TaskbarCreated` 자가 복구 | **기능적으로 확인.** 뒤에서 `NIM_DELETE`로 아이콘을 지운 뒤(`GetRect` → `0x80004005`) `TaskbarCreated`(`0xC0BC`)를 보내자 `hr=0x0`으로 복귀. **explorer.exe는 재시작하지 않았다** — 합성 메시지다 |

### 4.1 Windows 11이 새 트레이 아이콘을 숨긴다

새로 등록한 `NotifyIcon`은 **오버플로 플라이아웃**에 들어간다. 도달에 **클릭 두 번**(셰브론 → 아이콘)이 필요했다.

그리고 **`Shell_NotifyIconGetRect`가 문서화된 `S_FALSE`가 아니라 `S_OK`와 함께 셰브론의 사각형을 반환했다.** HRESULT를 믿으면 조용히 틀린 좌표를 얻는다.

**함의**: 첫 실행 UX는 *"트레이 아이콘이 안 보인다"* 다. FR-08-1은 이것을 다뤄야 한다.

| **다중 모니터 / 보조 작업표시줄** | 주 모니터만 사용 | 이 장비에 `Shell_SecondaryTrayWnd`가 (-1920,1188)에 있다 |

## 6. 측정 방법론상의 함정 — 기록해 둔다

1. **프로세스가 자기 자신에게 `SendInput`을 하면 그 프로세스가 포그라운드 권리를 얻는다.** 클릭이 다른 창에 떨어져도 그렇다. 첫 대조군이 이 때문에 **거짓 양성**을 냈다. 이후 모든 측정은 별도 `Clicker.exe`로 주입했다. **Q17류 측정에서 자기 프로세스 입력 주입은 무효다.**
2. **이 장비의 포그라운드 잠금 시간이 기본값이 아니다.** `SPI_GETFOREGROUNDLOCKTIMEOUT` = **2147483647 ms**, 레지스트리 `ForegroundLockTimeout` = **200000**. 값을 **읽기만** 했고 쓰지 않았다. 실제 값이 기본보다 **더 엄격**하므로 §1.1의 양성 결과는 **보수적**이다 — 더 관대한 장비에서 실패할 이유가 없다.
3. 마샬링은 `SPI_GETFOREGROUNDFLASHCOUNT`=7이 레지스트리와 일치함으로 검증했다.

## 7. 설계에 미치는 영향

| # | 사실 | 설계 요구 |
|---|---|---|
| S1 | 트레이 클릭 → 활성화는 우회 없이 성공한다 | D18의 활성화 부분은 **그대로 유효하다.** 우회 코드를 넣지 않는다 |

| S4 | `NOACTIVATE`는 명시적 `Activate()`도 무해화한다 | 오버레이의 포커스 탈취 경로가 구조적으로 부재. 별도 방어 불필요 |

| S7 | `IsActive`는 실패 시에도 `True`다 | 활성화 성공 판정은 `GetForegroundWindow()`로만 한다. 테스트도 마찬가지 |
| S8 | `AttachThreadInput`은 잠금 우회다 | **금지 목록에 명시한다.** 코드 리뷰에서 잡아야 한다 |
| S9 | 독점 전체화면 미측정 | S3는 이 경우를 **알려진 미검증 위험**으로 문서화한다. 구현 착수 시 실물 1회 확인 |
| S10 | **`AllowsTransparency=true`가 ClearType을 끈다** (§8) | 오버레이 창 구성을 **`AllowsTransparency=false` + `WS_EX_LAYERED`**로 전환한다. 되돌릴 수 없는 결정이 아니지만, 되돌리면 글자가 뭉개진다 |
| S11 | 성장 시 1프레임 미도색 띠, 축소 시 없음 (§9) | 자동 높이 갱신은 **성장 방향에서만** 한 프레임의 배경 노출을 낳는다. `SizeToContent=Height`가 명시 `Height`보다 낫다 |
| S12 | 확장 스타일·`Topmost`는 리사이즈·모니터 이동을 견딘다 (§9) | **재적용 코드를 넣지 않는다.** 16단계 내내 `0x08080028` 불변 |
| S13 | `RenderTargetBitmap`은 화면 안티에일리어싱을 반영하지 않는다 (§8.4) | 렌더링 품질 검증 테스트는 **화면 캡처로만** 한다. RTB 기반 단언은 무효다 |
| S16 | **WPF `Window`는 `AllowsTransparency=false`에서 레이어드가 될 수 없다** (§11.1) | 오버레이는 **생 Win32 부모 + WPF 자식**이어야 한다. §8.1 4행·§8.6의 구성은 무효 |
| S17 | 부모의 키·알파가 **자식이 그린 픽셀에 그대로 적용**되고 ClearType도 자식에서 살아남는다 (§11.2) | 이 구조가 목적을 실제로 달성한다. 선명한 글자와 투명이 양립한다 |
| S18 | **WPF `Popup`은 자기 최상위 HWND를 만들어 부모의 레이어드 경로 밖에 있다** (§11.4) | 툴팁·컨텍스트 메뉴·팝업에 키/알파가 적용되지 않는다. 키가 필요한 것을 팝업으로 만들지 마라 |
| S14 | **`SendMessageTimeout`의 성공 반환은 ack이 아니다** (§10.1) | 단일 인스턴스 신호의 확인은 **`lpdwResult`와 센티널의 일치**로만 판정한다. HLD D18-d·S3 `D-SH18`의 근거 |
| S15 | 지연 방출 루프는 **경계 트리거 + 래치**에서만 수렴한다 (§10.3) | `>= N` 임계 검사로 구현하면 자기 지속 폭주가 된다. S3 §8.4/§10.1이 래치를 명문화하는 근거 |

## 8. Q5 — `AllowsTransparency`와 텍스트 렌더링

측정일 2026-08-15. 시스템 ClearType은 켜져 있다(`SPI_GETFONTSMOOTHING=1`, `TYPE=2`). 판정 기준: **ClearType은 글리프 가장자리에 색수차 픽셀(R≠G≠B)을 남기고, 그레이스케일 AA는 중성 픽셀만 남긴다.**

### 8.1 핵심 결과

| 구성 | 색수차 잉크 픽셀 비율 | maxChroma | 판정 |
|---|---|---|---|
| 일반 창 (`AllowsTransparency=false`) | **90.4%** (626/692) | 142 | ClearType **켜짐** |
| `WindowStyle=None` + **`AllowsTransparency=true`** | **0.0%** (0/521) | **0** | ClearType **꺼짐** |
| 위 + `WS_EX_LAYERED\|TRANSPARENT\|NOACTIVATE` | **0.0%** | 0 | ClearType **꺼짐** |
| ~~**`AllowsTransparency=false` + `WS_EX_LAYERED` + `SetLayeredWindowAttributes`**~~ | ~~90.29~90.46%~~ | — | **⚠ 반증됨 → §11.1.** WPF `Window`는 이 구성에 **도달할 수 없다**. 이 행이 잰 것은 레이어드 창이 아니라 **비트가 조용히 걸러진 불투명 창**이었다 |

### 8.2 복구할 수 없다 — 시도하고 실패한 것들

### 8.3 프레임 비용은 문제가 아니었다

|---|---|---|---|
| `AllowsTransparency=false` | 6.06 ms | 6.06 ms | 4,625 ms |
| `AllowsTransparency=true` | 6.06 ms | 6.06 ms | 5,000 ms |

### 8.4 브리핑 전제 두 개가 틀렸다

1. **`RenderTargetBitmap`은 이 측정의 도구가 될 수 없다.** **일반 창을 포함한 모든 구성에서 그레이스케일을 반환**했다 — 화면이 90.29%를 보이는 자리에서 RTB는 0.00%였다. 기준선 12행 중 9행이 화면 캡처와 불일치했다. RTB에 기반한 렌더링 품질 결론은 전부 무효다.
2. **"프레임 비용"은 실재하는 우려가 아니었다.** §8.3 참조.

### 8.5 정직한 단서 — 손실의 성격

휘도만 보는 척도에서 그레이스케일은 "더 흐리지" 않다. 총 잉크 커버리지가 사실상 같고(402.2 대 402.5) 오히려 **더 좁다**(530 대 680 잉크 픽셀, 부분 커버리지 58.3% 대 67.5%). ClearType의 이득은 색 채널이 나르는 **3배의 수평 표본화 해상도**이며, 휘도 척도로는 보이지 않는다.

**따라서 손실은 획이 뭉개지는 것이 아니라 획 위치의 정밀도다.** 작은 글자의 숫자 구별(`8`/`6`, `3`/`9`)과 소수점 위치에서 드러난다 — 이 앱이 하는 일 그 자체다. 다만 "읽기 실험"을 한 것은 아니므로, 픽셀 데이터가 증명하는 것은 **정보량이 1/3로 줄었다**는 것이지 사람이 못 읽는다는 것이 아니다.

### 8.6 채택 구성과 그 대가

> **⚠ 이 절의 구성은 WPF `Window`에서 성립하지 않는다 — §11.1이 반증했다.** 채택 구성은 **생 Win32 레이어드 부모 + WPF `HwndSource` 자식**이며 §11.3에 있다. 아래 「잃는 것」과 세 가지 함정은 컬러키 방식 자체의 성질이므로 **그대로 유효하다.**

```
WindowStyle        = None
AllowsTransparency = false          ← 결정적 변경
ResizeMode         = NoResize
ShowInTaskbar      = false
Topmost            = true
SizeToContent      = Height
TextOptions.TextFormattingMode = Display    // 부분 커버리지 55.7% 대 58.3%

// SourceInitialized 이후
SetWindowLong(GWL_EXSTYLE, ex | WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE);
SetLayeredWindowAttributes(hwnd, key, alpha, LWA_COLORKEY | LWA_ALPHA);
```

**잃는 것 — 픽셀 단위 알파.** 안티에일리어싱된 둥근 모서리, 부드러운 그림자, 그라데이션 페이드가 불가능하다. 컬러키 투명은 **이진(binary)이고 가장자리가 딱딱하다.** 알파는 창 전체에 균일하므로 "한 패널은 불투명, 다른 패널은 50%" 같은 구성이 불가능하다.

> **투명도 슬라이더(FR-05)는 영향받지 않는다.** `LWA_ALPHA`가 창 전체 균일 알파를 그대로 제공한다.

**세 가지 함정** 【측정】

| # | 함정 |
|---|---|
| 1 | **키 영역 위에 텍스트를 직접 그리지 마라.** 컬러키 영역 위 글리프는 안티에일리어싱이 키 색으로 오염된다 — `Grayscale`·`Aliased` 행조차 73% 색수차(maxChroma 162)를 보였는데, 이는 ClearType이 아니라 **자홍색 후광**이다. 텍스트는 반드시 불투명한 비-키 패널 위에 앉아야 한다 |
| 2 | 콘텐츠 픽셀이 우연히 키 색과 같으면 **구멍이 된다.** 팔레트가 절대 쓰지 않는 색을 키로 골라야 한다 |
| 3 | `AllowsTransparency=false`에서 `Background="Transparent"`는 **불투명 검정**으로 렌더된다(실측 bg = (0,0,0)). 비침이 아니다 |

## 10. 2라운드 측정 — 단일 인스턴스 신호와 방출 루프

측정일 2026-08-16. S3 제3판 리뷰 중 수행했으며, **둘 다 동결 문서(HLD)의 설계를 바꿨다.**

### 10.1 `SendMessageTimeout`의 성공 반환은 처리 완료를 뜻하지 않는다

수신측이 `HWND_MESSAGE` 창을 만들되 `GetMessage`를 돌리지 않는 상태 — 즉 해체 구간(a단계 「수신 비활성화」 이후)이나 펌프 시작 전 구간 — 에서 `DestroyWindow`가 호출되면, **대기 중이던 크로스프로세스 `SendMessageTimeout`이 성공으로 풀린다.**

| 실행 | 타임아웃 설정 | 반환 | `GetLastError` | 경과 | 핸들러 실행 |
|---|---|---|---|---|---|
| 1 | 2,000 ms | **`0x1` (성공)** | `0` | 1,978 ms | **없음** (`ackPayload=0x0`) |
| 2 | 8,000 ms | **`0x1` (성공)** | `0` | 1,467 ms | **없음** (`ackPayload=0x0`) |

실행 2는 자기 타임아웃보다 **6.5초 먼저** 성공을 보고했다. 두 경우 모두 수신측 로그상 핸들러가 한 번도 실행되지 않았다 — 진짜 핸들러라면 센티널 `0x3039`를 `lpdwResult`에 남긴다.

**함의**: 반환값만 보면 두 번째 인스턴스가 「첫 인스턴스가 처리했다」고 오판하고 아무것도 하지 않는다. 메시지 상자도, 설정 창도 없다. 트레이가 죽었을 때의 **유일한 회수 경로가 조용히 무동작**한다.

**채택**: ack은 **`lpdwResult`가 핸들러가 정한 센티널과 일치할 때만** 성립한다. 성공 반환 + 센티널 불일치는 무응답과 동일하게 처리한다.

### 10.2 타임아웃은 「죽었음」과 구별되지 않는다

수신측이 핸들러 **안에서** 6초간 정상 처리 중인 경우:

| 관찰 | 값 |
|---|---|
| 발신측 | 2,008 ms에 `ERROR_TIMEOUT`(1460)으로 정상 타임아웃 |
| 수신측 | **끝까지 처리하고 약 4초 뒤 설정 창을 띄운다** |

즉 「잠시 바쁜 인스턴스」와 「죽은 인스턴스」가 발신측에서 같은 신호를 낸다. 사용자는 「도달 불가」 대화상자를 본 직후 설정 창이 저절로 뜨는 것을 본다. **설계는 이 중간 상태를 인정하고 문구를 그에 맞춰야 한다.**

### 10.3 지연 방출 루프 — 경계 트리거일 때만 수렴한다

`SnapshotFanout`의 재진입 가드 하에서 진단 호출을 버퍼링했다가 가드 해제 직후 방출하는 설계에 대해:

| 구현 | 결과 |
|---|---|
| **경계 트리거 + 래치** (문서 의도) | 실패 구독자 2개에서 **총 7회 패스 후 영구히 0.** 3초 추가 관측에서 증가 0 — **자기 제한적** |
| **`>= N` 레벨 검사** (흔한 방어적 구현) | 외부 자극 0에서 **초당 약 128,600회 `Republish`, 257,100회 `Store` 명령.** UI 스레드와 `Store` 소비 스레드를 동시에 태운다 |

**「필연적 폭주」라는 초기 의심은 반증됐다** — 문서 의도대로 구현하면 안전하다. 위험한 것은 **문서가 래치를 요구하지 않는다는 사실**이며, S2 §6.3의 「병합·중복 제거 없음」이 유일한 방어벽마저 제거한다.

**채택**: S3 §8.4/§10.1이 **경계 트리거와 「이미 보고함」 래치를 명문화**한다. 병합이 순환을 흡수한다는 서술은 거짓이므로 삭제한다 — 병합은 동시에 대기 중인 게시를 합칠 뿐, 스스로 방아쇠를 재생성하는 순환은 감쇠시키지 못한다.

## 11. 3라운드 측정 — 레이어드 부모 + WPF 자식

측정일 2026-08-16. 구현 6단계가 §8.1 4행을 반증하면서 시작됐고, **대체 구조가 성립하는지**를 확정하기 위해 수행했다.

환경: Win11 26200 · .NET 8.0.424 · 1920×1080 **96 DPI(배율 1.0)** · `DwmIsCompositionEnabled=True` · ClearType 켜짐(`FontSmoothing=2`, `FontSmoothingType=2`, RGB) · `RenderCapability.Tier=0x20000`. 배경 RGB(16,128,240), 회색 띠 RGB(128,128,128). 표본은 전부 `BitBlt(SRCCOPY|CAPTUREBLT)` 화면 캡처의 6×6 평균이다.

### 11.1 WPF `Window`는 `AllowsTransparency=false`에서 레이어드가 될 수 없다 — §8.1 4행 반증

네 경로 전부에서 **성공 반환(`ret=0`, `err=0`)인데 `GWL_EXSTYLE`은 변하지 않는다** — `SourceInitialized`, `Show()` 이후, `ContentRendered`, 그리고 비트를 미리 넣어 만든 `HwndSource`. 이어진 `SetLayeredWindowAttributes`는 **87(ERROR_INVALID_PARAMETER)** 로 실패한다. **같은 프로세스의 생 Win32 팝업은 즉시 받아들인다**(EXSTYLE `0x00080080`, 반환 `True`).

**§8.1 4행이 잰 것은 레이어드 창이 아니었다.** 비트가 조용히 걸러진 **불투명 `WindowStyle=None` 창**이었고, 그래서 ClearType이 살아 있었다. 그 행이 증명한 명제는 「레이어드 WPF 창이 ClearType을 유지한다」가 아니라 **「불투명 WPF 창이 ClearType을 유지한다」**다.

> **측정이 권위를 잃는 다섯 번째 방식** — 앞의 넷과 달리 **시험 대상 구성 자체가 성립한 적이 없었다.** 스타일 설정 호출이 성공을 반환한다는 사실만 확인하고 **읽어서 대조하지 않은** 것이 원인이다.

### 11.2 부모의 키·알파는 자식이 그린 픽셀에 그대로 적용된다

### 11.3 자식에서 ClearType이 완전히 살아남는다 — 이 구조의 존재 이유

> **이 표의 수치는 WPF 기본 서체의 것이다** 【2026-08-16 추가】. D-SH22가 서체를 Pretendard로 바꿨으므로 아래 잉크·색수차·spread 값은 **현재 형상을 설명하지 않는다.** 재측정은 **두 번 시도해 두 번 다 하지 못했다** — 처음에는 캡처 경로를 찾지 못해서(§13.3), 두 번째에는 캡처 경로를 찾고 보니 **WPF가 화면에 픽셀을 전혀 내지 않아서**다(§13.5). 이 표가 남는 이유는 그 세 열이 아니라 **행 사이의 관계** — 레이어드 부모+자식이 불투명 창과 같고, `AllowsTransparency=true`가 강제 그레이스케일과 같다는 것 — 이며, 그 결론은 서체와 무관하다.

| 불투명 WPF `Window` (대조) | 3,010 | **90.8%** | **111.11** |
| 강제 `Grayscale` (음성 대조) | 2,353 | **0.0%** | 0 |
| **`AllowsTransparency=true`** (음성 대조) | 2,353 | **0.0%** | 0 |

앞의 둘이 **비트 단위로 같다.** 그리고 마지막 행이 **옛 설계가 ClearType을 잃은 이유를 확증**한다 — `AllowsTransparency=true`가 강제 그레이스케일과 수치까지 동일하다.

**단서 하나** — α를 낮추면 서브픽셀 효과가 **감쇠**한다. α=128에서 색수차 **개수는 동일**(2,732, 90.8%)하지만 평균 spread가 **55.74 = 111.11 × 0.502**로 절반이 된다. 글자는 여전히 ClearType이지만 **더 부드럽게 읽힌다.** 투명도 슬라이더를 낮출수록 판독성이 점진적으로 떨어진다는 뜻이며, 이는 설계가 예상하지 못한 결합이다.

글리프 가장자리가 우연히 키 색에 걸리는 사고는 없었다 — 텍스트 패널 66,000px에서 배경색 픽셀 **0개**.

### 11.4 입력 라우팅

| 상황 | 결과 |
|---|---|
| 부모에 `WS_EX_TRANSPARENT` | `WindowFromPoint`가 **네 지점 전부**(자식 위 포함) 뒤 창을 반환. 외부 프로세스 주입 클릭이 배경의 올바른 지역 좌표에 착지 |
| `WS_EX_TRANSPARENT` 없음 | `WindowFromPoint`가 **자식 hwnd** 반환. 주입 클릭이 `WM_LBUTTONDOWN` → WPF `MouseLeftButtonDown` (309,69)로 정상 라우팅 |

자식의 EXSTYLE은 `0x0`인데도 **히트를 삼키지 않는다.** 클릭 통과가 부모 수준에서 전 영역에 걸린다.

주입은 **별도 프로세스**에서 했다 — 같은 프로세스의 `SendInput`은 호출자에게 포그라운드 권리를 주어 결과를 무효화한다(§6-1).

### 11.5 채택 구성

**부모 — 생 `CreateWindowEx`. WPF `Window`를 쓰지 않는다.**

```
exStyle : WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_TOPMOST | WS_EX_NOACTIVATE
          (+ 클릭 통과가 필요한 동안만 WS_EX_TRANSPARENT — 런타임 토글로 모드 전환)
style   : WS_POPUP | WS_VISIBLE | WS_CLIPCHILDREN
SetLayeredWindowAttributes(hwnd, 0x00FF00FF, alpha, LWA_COLORKEY | LWA_ALPHA)  // 1회면 된다
WM_PAINT: 클라이언트 전체를 채운다. 자식이 덮지 않는 영역은 키 색으로
```

**`WS_CLIPCHILDREN`이 없으면 부모의 `WM_PAINT`가 자식을 덮어 그린다.**

**자식** — `HwndSourceParameters { ParentWindow = parent, WindowStyle = WS_CHILD|WS_VISIBLE|WS_CLIPSIBLINGS, UsesPerPixelOpacity = false }`. `TextRenderingMode`는 `Auto`로 둔다(이미 ClearType로 해석된다), `TextFormattingMode = Ideal`. 투명해야 할 영역은 `#FF00FF`로 칠한다.

### 11.6 잃는 것

| 기능 | 상태 |
|---|---|
| `SizeToContent` | `HwndSource.SizeToContent`는 **동작하지만 자식 HWND만** 줄인다(640×400 → 88×16, 부모는 640×460 그대로). 크기 변경을 후킹해 **부모를 직접 `SetWindowPos`** 해야 한다 |
| `DragMove` | **없다.** `Window`가 없으므로 `WM_NCHITTEST` → `HTCAPTION`이나 수동 `WM_LBUTTONDOWN` + `SetWindowPos`로 재구현 |
| `Owner` | **된다.** `new WindowInteropHelper(w).Owner = parentHwnd`가 `GWLP_HWNDPARENT`를 설정한다(일치 확인) |
| **`Popup`** | 열리기는 하지만 **자기 최상위 HWND를 만들어 부모의 레이어드 경로 밖에 있다.** 키·알파가 적용되지 않는다 — **키가 필요한 것을 팝업·툴팁·컨텍스트 메뉴로 만들지 마라** |
| 컬러키의 이진성 | 픽셀 단위 알파가 없으므로 부드러운 그림자·안티에일리어싱된 바깥 모서리 불가 |
| 그 외 | `Window` XAML 루트, `WindowState`, 호스트의 `ShowDialog`, `Window` 수준 `Closing`/`Activated` |

### 11.7 미측정

- **안티에일리어싱된 둥근 투명 모서리.** 측정한 키 영역은 전부 축 정렬 정수 사각형이었고 경계는 픽셀 단위로 정확했다(x=549 배경, x=550 내용, 헤일로 없음). 둥근 모서리의 블렌드된 가장자리 픽셀은 `0xFF00FF`와 같지 않으므로 **마젠타 헤일로가 보일 것**이다 — `LWA_COLORKEY`의 성질상 그렇게 되나 **UNVERIFIED**.
- 다중 모니터 · 혼합 DPI (이 장비는 단일 모니터 96 DPI).
- **실물 PoE 클라이언트 위에서의 동작** — 여기서는 다른 WPF 창이 배경이었다.
- 레이어드 합성의 장시간 안정성 (프로브 수명 약 10초).

## 12. 4라운드 측정 — 실물 앱에서의 확인 (D-SH20 구현 후)

측정일 2026-08-16. 프로브가 아니라 **빌드한 앱 자체**를 띄우고 외부 프로세스에서 재었다. 배경은 RGB(16,128,240) 전체화면 폼, 화면 캡처는 `BitBlt(SRCCOPY|CAPTUREBLT)`.

### 12.1 구조가 실제로 성립한다

| 측정 | 값 |
|---|---|
| 부모 `GWL_EXSTYLE` | **`0x080800A8`** = `LAYERED\|TOOLWINDOW\|TOPMOST\|NOACTIVATE\|TRANSPARENT` — §11.5 채택 구성 그대로 |
| 부모 `GWL_STYLE` | **`0x96000000`** = `POPUP\|VISIBLE\|CLIPSIBLINGS\|CLIPCHILDREN` |
| `GetLayeredWindowAttributes` | **`True`**, `key=0xFF00FF`, `alpha=222`, `flags=0x3`(`COLORKEY\|ALPHA`) |
| 설정 창 `GWL_EXSTYLE` | **`0x00040108`** — `WS_EX_TOPMOST` 전파됨. §2가 예측한 `0x40108` 그대로이며, 이번엔 관리형 `Owner`가 아니라 `WindowInteropHelper.Owner`(`GWLP_HWNDPARENT`)로 지정했다 |

**`alpha=222`는 `0.87 × 255 = 221.85`의 반올림이다.** 저장된 설정값이 `LWA_ALPHA`까지 그대로 도달한다.

### 12.2 투명도는 산술적으로 확인된다

오버레이 사각형을 배경 위에서 캡처해 평균 색을 재고, 바로 숨긴 뒤 같은 사각형을 다시 재 배경을 얻었다.

| 상태 | 측정 평균 | 예측 |
|---|---|---|
| 오버레이 없음(배경만) | (16, 128, 240) | — |
| 오버레이 α=222, 텍스트 없는 띠 | **(28, 43, 57)** | (28.2, 42.7, 57.2) — `#1E1E1E`를 α=0.871로 블렌딩 |
| 오버레이 전체, 불투명(α=255) | (33.2, 33.2, 33.2) | 배경의 파란이 **0** — 완전 불투명 |
| 오버레이 전체, α=128 | **(24.6, 80.6, 136.6)** | 배경과 본문의 중간 |

**예측과 측정이 소수점 한 자리에서 일치한다.** 오버레이는 실제로 투명하며, 슬라이더는 실제로 동작한다.

### 12.3 슬라이더 → `LWA_ALPHA`, UI 자동화로 구동

설정 창의 슬라이더를 UI Automation으로 직접 움직이고 부모의 알파를 다시 읽었다 — 파일을 고쳐 재시작한 것이 아니라 살아 있는 `Changed` 경로를 탄 것이다.

| 슬라이더 | 읽은 `LWA` 알파 | 기대치 |
|---|---|---|
| 1.00 | **255** | 255 |
| 0.50 | **128** | 128 |
| 0.75 | **191** | 191 |

슬라이더의 `Minimum`은 **0.5**로 읽혔다(D-SH21).

### 12.4 클릭 통과와 이동 모드

- 오버레이 중앙에서 `WindowFromPoint` → **배경 폼의 hwnd**. 자식이 덮고 있는 지점에서도 통과한다 — §11.4와 일치.
- 이동 모드 ON → EXSTYLE `0x08080088`(`TRANSPARENT` 빠짐), OFF → `0x080800A8`. `NOACTIVATE`도 `LAYERED`도 그대로다.

### 12.5 자동 높이

관심목록에 항목 1건을 추가하자 부모 사각형이 **420×44 → 420×61**로 바뀌었다. 자식의 `WM_SIZE`를 부모가 따라가는 경로가 실제로 동작한다.

### 12.6 이 측정이 드러낸 결함 둘

1. **동결된 빌드의 오버레이는 내용이 없었다.** 모든 콘텐츠가 `Visibility="Collapsed"`인 이동 모드 테두리 안에 들어 있어, 창은 **420×8px의 빈 띠**로 렌더됐다. 레이어드 전환과 무관한 선행 결함이며, 오버레이가 한 번도 보이지 않았기 때문에 아무도 못 봤다. → S3 §4.6.
2. **이동 모드 진입 시 높이를 `ActualHeight`로 고정하면 `외 n개 더`가 1에 래치된다.** 레이아웃 라운딩 때문에 고정값이 콘텐츠보다 1px 미만 작을 수 있고, 마커가 뜨면 마커 자신의 높이가 여유를 더 깎아 자기 유지된다. 관심목록 1건인데 그 행 옆에 `+1 more`가 뜨는 것을 화면에서 보고 찾았다. → S3 §4.4.

### 12.7 여전히 미측정

§11.7의 네 항목(둥근 모서리, 혼합 DPI, 실물 PoE 클라이언트, 장시간 안정성)은 그대로 남는다. 이 측정은 앱 수명 약 1분, 단일 96 DPI 모니터, 배경은 PoE가 아니라 WinForms 창이었다. **서브픽셀 선명도는 재지 않았다** — §11.3을 그대로 믿고 있으며, 화면으로 본 글자가 선명하다는 인상은 측정이 아니다.

### 12.8 컬러키는 출하 형상에서 죽은 코드다 — 키 영역 동작 전부가 미검증

**측정.** 출하 형상(420×163, 관심목록 1건)의 오버레이 사각형 안에서 **68,460 픽셀 중 키 색(`0xFF00FF`)인 픽셀은 0개**였다. 이유는 단순하다: 본문 `Border`(`#1E1E1E`)가 창 전체로 늘어나므로 루트 `UserControl`의 키 배경이 **드러나는 자리가 없다.** 화면에서 보이는 투명함은 전부 `LWA_ALPHA`(§12.2에서 산술로 확인)에서 나온다.

**그래서 무엇이 바뀌나 — 아무것도 바뀌지 않는다.** 레이어드 재구축(D-SH20)의 근거는 컬러키가 아니라 **알파와 ClearType**이다. `LWA_ALPHA`도 `WS_EX_LAYERED`를 요구하고, WPF `Window`는 `AllowsTransparency=false`에서 그 비트를 아예 갖지 못한다(§11.1). 따라서 키가 쓰이지 않는다는 사실은 구조를 되돌릴 근거가 되지 못한다. `LWA_COLORKEY`는 그대로 두되(비용은 플래그 한 비트다), **아래 항목들은 "설계가 서술하지만 출하 형상에서는 한 번도 실행되지 않은 동작"으로 분류한다.**

| 문서가 서술하는 키 영역 동작 | 실제 검증 상태 |
|---|---|
| 키 영역은 클릭을 통과시킨다(HLD D4-c, S3 §4.0.1의 이진 경계) | **미검증.** 통과하는 키 픽셀이 존재하지 않는다. §12.4에서 관측한 클릭 통과는 `WS_EX_TRANSPARENT`가 창 전체에 건 것이지 키가 한 것이 아니다 |
| 키 영역 위의 글리프는 자홍색 후광을 얻는다(§8.6 trap 1) | 여전히 참인 **측정**이지만 출하 형상에서는 **도달 불가능한 위험**이다 — 키 픽셀이 없으므로 그 위에 글자를 놓을 자리도 없다 |
| 그립은 "칠해진 픽셀 안으로" 넣어야 한다(S3 §4.6.2) | 근거였던 제약이 출하 형상에는 존재하지 않는다. 규칙 자체는 유지한다 — 본문 `Border`가 창을 다 덮지 않는 형상으로 바뀌면 곧바로 되살아난다 |
| 콘텐츠 픽셀이 우연히 키 색과 같으면 구멍이 된다(S4 §15.1) | **미검증이며 현재 형상에서는 발생할 수 없다.** 팔레트가 확정되면(S3 §14-12) 이 표를 다시 읽어야 한다 |

**기록해 두는 이유.** 이 넷은 어느 것도 "틀렸다"가 아니라 **"이 형상에서는 시험된 적이 없다"** 이다. 그 구별을 남기지 않으면 다음 사람이 표의 왼쪽 열을 검증된 사실로 읽는다.

## 13. 5라운드 — 서체 교체(D-SH22)와 **취소된 ClearType 재측정**

측정일 2026-08-16. 환경: Win11 Pro 10.0.26200 · .NET SDK 8.0.424 · 96 DPI · `DwmIsCompositionEnabled=True` · `SM_REMOTESESSION=0`(원격 세션 아님) · `HKCU\Control Panel\Desktop`의 `FontSmoothing=2`, `FontSmoothingType=2`(ClearType), `FontSmoothingOrientation=1`(RGB) · `RenderCapability.Tier=0x20000`(하드웨어) · `HKCU\SOFTWARE\Microsoft\Avalon.Graphics` **키 없음**(가속 무력화 흔적 없음, 측정 후에도 없음).

### 13.1 §11.3의 수치는 이제 서체가 다른 구성의 것이다

§11.3(잉크 3,010 · 색수차 **90.8%** · 평균 spread **111.11**)은 **WPF 기본 서체**로 잰 값이다. D-SH22가 두 창의 서체를 Pretendard로 바꿨으므로 **그 수치는 현재 형상을 설명하지 않는다.** 아래 13.3의 이유로 새 수치를 얻지 못했으므로, §11.3은 **"기본 서체에서의 값"으로만** 읽어야 한다. 지우지 않는 이유는 그것이 여전히 「레이어드 부모 + WPF 자식이 불투명 창과 비트 단위로 같다」와 「`AllowsTransparency=true`가 ClearType을 죽인다」를 증명하기 때문이다 — 그 결론들은 서체와 무관하다.

### 13.2 서체 해석은 확인했다 — 화면이 아니라 타이프페이스로

| 확인 | 방법 | 결과 |
|---|---|---|
| 앱이 실제로 Pretendard를 잡는가 | 실물 앱 기동, 로그(`Composition`) | **`Typeface Pretendard resolved from the bundled resource (4 faces)`** — 두 얼굴 × 이탤릭 시뮬레이션 |
| XAML 속성 문자열이 해석되는가 | 별도 WPF 프로세스에서 `XamlReader.Parse`, BaseUri를 `pack://application:,,,/<asm>;component/…xaml`로 두고 4개 형식 비교 | `pack://application:,,,/Fonts/#Pretendard` → **Pretendard**, `/Fonts/#Pretendard` → **Pretendard**, `<asm>;component/Fonts/#Pretendard` → **Pretendard**, `./Fonts/#Pretendard` → **UNRESOLVED** |
| 리소스 바이트가 진짜 Pretendard인가 | `BundledFontTests`(S4 §16.10) | 패밀리 `Pretendard`, 한글 11,172음절 커버, Regular/SemiBold |

**【측정】 코드에서 `new FontFamily("pack://application:,,,/Fonts/#Pretendard")`는 해석되지 않는다.** 문자열 생성자에는 리소스를 풀 기준 URI가 없어 **조용히 폴백**한다(반환된 패밀리의 얼굴 수 14 = 폴백 패밀리). 같은 문자열이 **XAML 속성으로는 해석된다** — 파서가 XAML 자신의 BaseUri를 넘겨주기 때문이다. 코드에서 읽어 볼 때는 `new FontFamily(new Uri("pack://application:,,,/"), "./Fonts/#Pretendard")`처럼 기준 URI를 명시해야 하며, 그러지 않으면 **존재하지 않는 실패를 보고하게 된다.** `Fonts.GetFontFamilies(new Uri("pack://application:,,,/"), "./Fonts/")`도 같은 이유로 1개를 정확히 돌려준다.

### 13.3 ClearType 재측정 — **하지 못했다**

**결론: 이 장비에서 하드웨어 렌더된 WPF 표면을 픽셀로 읽어 낼 방법을 찾지 못했다. 따라서 서체 교체 후의 색수차·spread는 미측정이다.** 아래는 시도와 그 관측이다.

| 시도 | 관측 |
|---|---|
| §11.3과 같은 방식 — 화면 DC에서 `BitBlt(SRCCOPY\|CAPTUREBLT)` | **창이 캡처되지 않는다.** 프로브 창(레이어드 부모 + WPF 자식) 좌표에서 읽힌 것은 **그 뒤의 터미널 창**이었다. 서체를 바꿔 두 번 돌렸는데 픽셀 통계가 **완전히 동일**(ink 63,000 · 색수차 8,922 · 14.2%)했던 것이 그 증거다 — 캡처가 프로브를 담았다면 같을 수 없다 |
| 같은 지점의 `WindowFromPoint` | **자식 hwnd**를 반환한다. 창은 데스크톱에 있고 최상위이며 `IsWindowVisible=True`, `GetWindowRect`도 정확하다. **창이 없어서가 아니다** |
| `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT)` — 부모/자식 × 플래그 0/2, 네 조합 | 전부 **빈 표면**. 저장한 PNG는 균일한 흰색이다. 평범한 WPF `Window`(레이어드 아님)로 바꿔도 같다 |
| 소프트웨어 렌더링으로 우회 | **하지 않았다.** `DisableHWAcceleration=1`은 캡처를 되살리지만 그러면 서브픽셀 자체가 사라지므로 **재려는 값이 정의상 존재하지 않는다.** 잰 척한 수치를 남기는 것보다 미측정이 낫다 |
| `RenderTargetBitmap` | 애초에 무효다(§4.0.2·§8.4) |

**§4.0.2를 확장한다.** 그 절은 "렌더링 품질 검증은 화면 캡처로만 한다"고 적었다. 이번 라운드가 덧붙이는 사실은 **그 화면 캡처가 이 장비에서는 GDI 경로로 성립하지 않는다**는 것이다 — `BitBlt`는 데스크톱의 레거시 GDI 사본을 읽으므로 DWM이 합성하는 D3D 표면(=WPF가 그린 것)이 들어 있지 않고, `PrintWindow`도 빈 표면을 준다. **다음에 서브픽셀을 재려는 사람은 GDI 캡처부터 다시 시작하지 마라.** 남은 경로는 Desktop Duplication(DXGI) 또는 `Windows.Graphics.Capture`이며 **둘 다 이 라운드에서 시도하지 않았다**(미측정).

### 13.4 그래서 무엇이 열려 있는가

- **서체 교체 후의 색수차·평균 spread** — 미측정. §11.3의 90.8% / 111.11을 Pretendard에 그대로 옮겨 적으면 안 된다.
- Pretendard의 **12px 판독성** — S3 §14-12의 사람 판독 실험이 다룰 몫이다. 서체 크기는 여전히 잠정이다(S4 §15.1).
- 위 두 가지 모두 **캡처 경로가 확보되기 전에는 시작할 수 없다** — 실험의 선행 조건이 §13.3이다.
  【2026-08-16 정정】 캡처 경로는 §13.5에서 확보했다. 남은 선행 조건은 캡처가 아니라 **WPF 하드웨어 렌더가 화면에 픽셀을 내는 상태**다(§13.5.3).

### 13.5 6라운드 — 캡처 경로는 확보했다. 그런데 **WPF가 픽셀을 내지 않는다**

측정일 2026-08-16, §13.3보다 뒤. 환경: Win11 Pro 10.0.26200 · .NET SDK 8.0.424 · 1920×1080 · `GetDpiForSystem=96` · `DwmIsCompositionEnabled=True` · `SM_REMOTESESSION=0` · 입력 데스크톱 `Default` · 어댑터0 NVIDIA GeForce RTX 4070 Ti(`\\.\DISPLAY1`, attached) / 어댑터1 AMD Radeon(TM) Graphics(출력 없음) / 어댑터2 Basic Render Driver · `RenderCapability.Tier=0x20000`. 배경은 §11·§12와 같은 RGB(16,128,240) 전체화면 폼.

**결론 세 줄.**

1. §13.3이 내린 「이 기계에는 캡처 경로가 없다」는 진단은 **틀렸다.** 두 경로가 작동하고 서로 **바이트 단위로 일치**한다.
2. 그 경로로 보니 **출하 형상의 오버레이는 화면에서 검은 사각형이다.** 잴 글자가 없다.
3. 원인은 캡처가 아니라 **WPF의 하드웨어 렌더 경로**다. 같은 프로브를 `SoftwareOnly`로 돌리면 즉시 그려진다. 따라서 Pretendard의 색수차·평균 spread는 **이번에도 미측정**이다.

#### 13.5.1 캡처 경로 — 무엇이 되고 무엇이 안 되나

| 경로 | 결과 |
|---|---|
| `BitBlt(SRCCOPY\|CAPTUREBLT)` 화면 DC | **작동한다.** GDI/WinForms 창의 글자를 정확히 담는다 |
| **`Windows.Graphics.Capture` 모니터 캡처** (`IGraphicsCaptureItemInterop::CreateForMonitor` + `Direct3D11CaptureFramePool.CreateFreeThreaded`) | **작동한다.** DWM이 합성한 데스크톱 그대로 1920×1080 |
| `Windows.Graphics.Capture` 창 캡처 (`CreateForWindow`) | GDI 창은 정확. **레이어드 부모는 전부 검정**이고, 자식 HWND는 `E_INVALIDARG` — WGC는 자식 창을 캡처하지 않는다 |
| **DXGI Desktop Duplication** | **프레임이 오지 않는다.** 올바른 어댑터·출력에 `DuplicateOutput`은 성공하는데 `AcquireNextFrame`이 8초 내내 `DXGI_ERROR_WAIT_TIMEOUT(0x887A0027)`. 화면 구석에서 25 Hz로 색이 바뀌고 있어도 그렇다 |

**두 경로가 같은 것을 본다.** 같은 사각형을 `BitBlt`과 WGC 모니터 캡처로 찍어 픽셀 단위로 비교했다 — 네 경우 모두 **다른 픽셀 0개**:

| 대상 | 크기 | 불일치 |
|---|---|---|
| WinForms 창(GDI 글자) | 420×60 | **0** / 25,200 |
| 실물 앱 오버레이 | 420×107 | **0** / 44,940 |
| WPF 프로브(하드웨어) | 420×80 | **0** / 33,600 |
| WPF 프로브(소프트웨어) | 420×80 | **0** / 33,600 |

§13.3의 「`BitBlt`이 프로브 뒤의 터미널을 찍었다」는 **관측은 옳았고 해석이 틀렸다.** `BitBlt`은 데스크톱을 정확히 찍고 있었다. 그 자리에 **WPF 창이 없었을 뿐이다.**

#### 13.5.2 WPF가 화면에 아무것도 내지 않는다 — 세 대조

각 행은 `BitBlt`과 WGC 모니터 캡처 **양쪽에서 동일**하다.

| 창 | 캡처 결과 |
|---|---|
| WinForms 창(`#1E1E1E` 바탕 + `Label`) | **distinct=32**, `#1E1E1E`×24,584 · `#EDEDED`×67 — 글자가 보인다 |
| 전용 WPF 프로세스의 불투명 `Window`(§11.3 대조군 형상, 420×80, `Topmost`, `IsWindowVisible=True`, `GetWindowRect` 정확) | **distinct=1**, 전부 배경색 `#1080F0` — **창이 화면에 존재하지 않는다** |
| 실물 앱 오버레이(레이어드 부모 + WPF 자식, α=222) | **distinct=2** — 부모의 키 영역은 배경 `#1080F0`(31,653px), 자식 HWND 영역은 전부 **`#02111F`**(13,287px) |

`#02111F`는 **검정 콘텐츠를 α=222로 배경 위에 블렌딩한 값**이다: (0,0,0)×222/255 + (16,128,240)×33/255 = (2.07, 16.6, 31.0). 즉 **레이어드 합성은 정상 동작하고 있고 자식이 그린 것이 검정**이다. 같은 자리를 §12.2는 (28,43,57) = `#1E1E1E`의 블렌딩으로 쟀다 — **오늘 아침에는 자식이 본문을 그렸다**는 뜻이며, 그 사이에 기계 상태가 바뀌었다.

#### 13.5.3 원인은 하드웨어 렌더 경로다

프로브 **자신의 코드**에서 `RenderOptions.ProcessRenderMode = RenderMode.SoftwareOnly` 한 줄만 바꿔 같은 실행을 반복했다. 레지스트리는 읽지도 쓰지도 않았다.

| 프로브 | 캡처 |
|---|---|
| 기본(하드웨어, `Tier=0x20000`) | **distinct=1** — 아무것도 없다 |
| `SoftwareOnly` | **distinct=109**, `#1E1E1E`×31,017 · `#EDEDED`×178, 그리고 `#1D1D6A`·`#451D1D` 같은 색수차 픽셀 — **즉시 그려진다** |

Tier는 하드웨어(0x20000)라고 보고하는데 그 경로의 출력이 화면에 도달하지 않는다. **DWM은 살아 있다** — `DwmFlush()`가 `S_OK`로 **호출당 16.6~16.7 ms**(10회 155.2 ms), 정확히 60 Hz 합성이다. WinForms 창도 터미널도 정상 합성된다. 망가진 것은 **WPF의 D3D 경로 하나**이며, Desktop Duplication이 프레임을 전혀 못 받는 것도 같은 GPU 상태의 다른 증상으로 보인다(둘 다 NVIDIA 어댑터 쪽이고, D3D11 디바이스 생성 자체는 성공한다).

프로세스 계보 탓이 아니다 — 샌드박스 밖에서 `Start-Process`로 직접 띄운 같은 프로브도 결과가 같다.

#### 13.5.4 그래서 기록하는 값

**없다. Pretendard의 12px·10px 색수차와 평균 spread는 이번 라운드에서도 측정하지 못했다.** 4× 확대 이미지도 만들지 못했다 — 확대할 글자가 없다.

소프트웨어 렌더 프레임에서는 수치가 나온다(420×60 영역, 잉크 2,583 · 색수차 2,309 · **89.4%** · avgSpread **81.93**). **이 값을 §11.3 자리에 옮겨 적지 마라.** 소프트웨어 래스터라이저는 다른 래스터라이저이고 출하 형상은 하드웨어로 그린다. 여기 적는 유일한 이유는 **분석 코드가 실제로 색수차를 셀 수 있음을 보이는 것**이다 — 잉크 판정, spread 계산, PNG 왕복이 전부 동작한다. 즉 다음 라운드가 실패하면 그것은 분석기 탓이 아니다.

#### 13.5.5 다음 사람에게

1. **캡처는 이미 풀린 문제다.** `Windows.Graphics.Capture` **모니터** 캡처를 쓰고, 같은 사각형을 `BitBlt`으로도 찍어 **두 결과가 같은지 확인**하라. 오늘 네 번 다 0픽셀 차이였다. Desktop Duplication은 이 기계에서 쓰지 마라. `CreateForWindow`도 레이어드 창에는 쓰지 마라(검정을 준다).
2. **재기 전에 렌더가 살아 있는지부터 확인하라.** 전용 WPF 프로세스에 불투명 창 하나를 띄우고 그 사각형을 찍어 **배경색이 아닌 픽셀이 나오는지** 본다. 나오지 않으면 그날은 아무것도 잴 수 없다. §13.3과 이 라운드가 각각 반나절씩 태운 이유가 이 한 줄의 부재다.
3. 기계 상태를 되돌리는 수단(재부팅·디스플레이 드라이버 재시작)은 이 작업의 권한 밖이라 시도하지 않았다. `HKCU\SOFTWARE\Microsoft\Avalon.Graphics` 키는 지금 **존재하지만 값이 0개**다(§13이 「키 없음」이라 적은 것과 다르다). 값이 없으므로 `DisableHWAcceleration`은 설정되어 있지 않으며, 이 라운드는 레지스트리에 쓰지 않았다.

> **측정이 권위를 잃는 여섯 번째 방식** — §13.3은 **캡처가 실패했다**고 적었지만 실제로는 **캡처가 성공했고 찍을 것이 없었다.** 도구를 탓하기 전에 **작동하는 대조군을 같은 도구로 찍어 보라.** GDI 창 하나를 나란히 놓았으면 반나절이 아니라 5분에 갈렸다.
